<h2>一、先说清哪些能脚本化，哪些不能</h2>
<p>把环境拆成五层：浏览器本体、配置文件（Cookie、localStorage、IndexedDB）、渲染指纹（Canvas、WebGL、字体、屏幕参数）、网络层（代理、DNS、WebRTC）、账号层。前四层基本可控，第五层只能靠流程约束。</p>
<h3>可控的四层</h3>
<p>用独立的 user-data-dir 目录承载配置，用启动参数固定语言、时区、窗口尺寸，用代理参数固定出口，用固定的浏览器小版本号避免升级带来的指纹漂移。这四件事写成脚本，重复执行的偏差可以压到很小。</p>
<h3>不可控的三件事</h3>
<p>IP 的历史使用记录、出口所在网络的时延特征、平台侧对该账号的行为画像。这三项无法通过脚本还原，只能通过选择干净的出口和保持行为一致性来间接影响，且在平台规则允许的范围内操作。</p>

<h2>二、症状一：重建完立刻要求重新验证</h2>
<p>这是最高频的现象。环境刚拉起来，登录能过，但几分钟内就被要求再次确认，或者直接提示环境异常。故障树往下分两支：配置没带全，或者网络特征与之前不一致。</p>
<h3>分支 A：配置残留或缺失</h3>
<p>先确认新目录是不是真干净。用 ls 看 user-data-dir 下是否只有预期文件，重点查 Cookies、Local Storage、IndexedDB 三个位置。反过来，如果是“恢复”场景，常见问题是只还原了 Cookies 而漏了 IndexedDB，页面看起来已登录，实际会话凭据不完整，平台侧会认为状态异常。</p>
<h3>分支 B：网络特征跳变</h3>
<p>对比重建前后的出口地址、ASN、时区、语言四项。时区最容易出错：系统时区是东八区、出口在西欧，这种组合在任何平台上都不自然。判定方法是在页面控制台执行 Intl.DateTimeFormat().resolvedOptions().timeZone，与出口所在地比对，不一致就改启动参数或系统时区。</p>

<h2>三、症状二：页面能开，操作却被拒</h2>
<p>能打开说明连通性没问题，被拒通常发生在提交动作上。这一支的重点不在网络，而在渲染指纹与请求头的一致性。</p>
<h3>先查请求头与客户端是否自洽</h3>
<p>用浏览器开发者工具看 User-Agent、Accept-Language、sec-ch-ua 三处，与出口地区、页面语言对照。UA 写 Windows、实际跑在 Linux 容器里，或者语言头是英文而系统语言是中文，都属于明显的不自洽。这类问题不需要复杂工具，肉眼比对就能发现大半。</p>
<h3>再查渲染指纹的稳定性</h3>
<p>在控制台取 canvas 与 WebGL 的渲染结果哈希，同一台机器连续取五次应当一致。若每次不同，说明有随机化插件在起作用，这种不稳定本身就是异常信号。字体列表也建议固定，容器镜像里缺字体导致渲染差异是常见原因。</p>

<h2>四、症状三：代理显示已生效，出口却不对</h2>
<p>这一支最隐蔽，因为面板上绿灯亮着，实际请求可能走了别的路径。按“三层出口”逐个验证：浏览器代理、系统代理、DNS 解析。</p>
<h3>三条命令定位</h3>
<p>先用 curl -x http://代理地址:端口 https://ipinfo.io/json 看返回的 ip、org、country 是否符合预期；再在浏览器里访问同一接口，比对结果；最后用 dig 或 nslookup 指定 DNS 服务器查询一个域名，确认解析没有走本地运营商。三者结果不一致，问题就锁定在对应那一层。</p>
<h3>WebRTC 与 IPv6 的漏点</h3>
<p>浏览器可能通过 WebRTC 暴露本地地址，也可能优先走 IPv6 绕过只监听 IPv4 的代理。检查方法是在页面里取 RTCPeerConnection 的候选地址，看是否出现非代理网段；IPv6 则用 curl -6 测试是否可直连。处置方式是关闭 WebRTC 或限制候选类型，并在代理侧屏蔽 IPv6 出口。</p>

<h2>五、把故障树做成脚本，每次重建都跑一遍</h2>
<p>手工核查三次就会走样，写成脚本才能保证每次一致。建议把检查项做成一个可重复执行的清单脚本，重建后自动跑，输出一份对照报告。</p>
<h3>至少要覆盖的六项</h3>
<p>出口地址与 ASN、时区与语言、UA 与 sec-ch-ua、canvas 哈希稳定性、Cookie 与存储完整性、DNS 与 WebRTC 泄露。六项全绿再进入业务操作，能省掉大量“看起来好了其实没好”的返工。</p>
<h3>留一份基线快照</h3>
<p>首次配置成功后，把六项结果和关键配置导出成基线文件，之后每次重建都与基线逐项比对。差异项要能解释，解释不了的差异就是风险点。快照本身不含账号凭据，注意脱敏后再归档。</p>

<h2>常见问答</h2>
<h3>一键重建能连 IP 一起还原吗？</h3>
<p>答：地址可以还原到同一段，但该地址的历史使用情况无法还原。若原地址已被频繁使用，重建环境也不会改变它在平台侧的既有印象，这种情况更适合换一条长期稳定的出口。</p>
<h3>Cookie 备份要注意什么？</h3>
<p>答：备份要覆盖 Cookies、Local Storage、IndexedDB 三处，且在同一浏览器大版本下还原。跨版本还原常出现结构不兼容，表现为页面已登录但接口返回未授权。</p>
<h3>为什么重建后延迟反而变高了？</h3>
<p>答：先排除代理链路变化。对比重建前后的 traceroute 路径与首字节 P95，若路径多了一跳国际出口，说明出口节点变了；若路径相同而延迟上升，多半是线路拥塞，换个时段复测再判断。</p>
<h3>指纹要保持完全一致吗？</h3>
<p>答：不需要也不可能完全一致，浏览器小版本升级、字体增删都会带来细微变化。目标是稳定而不是复制：同一环境多次访问结果一致，同一账号的访问特征不要今天一个样明天一个样。</p>
